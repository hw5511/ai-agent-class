# 진행 방식 — 계획하고, 만들고, 근거를 만든다

> 출처: obra/superpowers 의 brainstorming · writing-plans · TDD · verification-before-completion 을 이 스택에 맞게 압축.

## 1. 코드보다 설계가 먼저다

구현을 시작하기 전에 **무엇을 만들 것인지 말로 적는다.**

- 만들 화면과 그 화면의 임무
- 쓸 shadcn 컴포넌트 목록
- 도메인 타입 (`Task`, `ColumnId` …)
- 되돌리기 어려운 선택과 그 이유

사람이 있으면 여기서 승인을 받는다.
사람이 없으면 **가정을 명시하고 진행한다.** 설계 단계 자체를 건너뛰지는 않는다.

## 2. 작은 조각으로 쪼갠다

각 조각은 그 자체로 동작해야 한다. 한 조각 = 파일 몇 개 + 확인 방법 하나.

```
1) 타입 + 초기 데이터        → 타입 에러 없음
2) 보드 레이아웃 (정적)       → 컬럼 3개가 보임
3) 카드 추가                 → 입력한 카드가 나타남
4) 카드 이동                 → 컬럼이 바뀜
5) 삭제 + 되돌리기           → 확인 없이 사라지지 않음
6) 담당자 필터 (URL 반영)     → 새로고침해도 유지됨
7) 빈 상태                   → 0건일 때 안내가 보임
```

## 3. 동작을 먼저 적는다

가능하면 테스트를 먼저 쓴다. 최소한 **"이게 되면 성공"을 조각마다 먼저 적는다.**
확인 방법을 정하지 않은 조각은 아직 시작할 준비가 안 된 것이다.

## 4. 완료를 주장하기 전에

**철칙: 근거 없이 완료를 말하지 않는다.**

이 메시지에서 실행하지 않은 명령의 결과를 "통과한다"고 말할 수 없다.

완료라고 쓰기 전에 확인한다:

- [ ] 타입 체크를 돌렸는가 — 출력을 봤는가
- [ ] 테스트를 돌렸는가 — 출력을 봤는가
- [ ] 요구사항을 하나씩 대조했는가
- [ ] `reference/interface.md` 로 자기 코드를 훑었는가
- [ ] 빈 상태 · 긴 입력 · 키보드 이동을 확인했는가

**실행할 수 없는 환경이면 "실행하지 못했다"고 그대로 쓴다.**
돌리지 않은 것을 돌린 것처럼 쓰는 것이 이 규칙을 어기는 유일한 방법이다.

## 5. 마지막에 하나 뺀다

만들고 나서 다시 본다. 브리프에 봉사하지 않는 장식을 하나 덜어낸다.
